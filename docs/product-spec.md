# Texas Hold'em 关键产品决策

> 状态：开发基线  
> 适用范围：`LeonemZhang/Texas_Holdem`  
> 本文描述产品目标、明确规则和关键交互。实现设计以 `docs/architecture.md` 为准。

## 1. 产品定位

本项目是一款供朋友之间通过实体局域网或虚拟局域网进行对战的无限注德州扑克游戏。

游戏不依赖公网服务。房主的 Windows 客户端同时运行房间服务器，其他玩家通过 Windows 客户端或浏览器连接房主。

### 1.1 核心目标

- 在虚拟局域网中稳定创建、发现和加入房间。
- 支持 Windows 桌面端和手机、电脑浏览器共同参与同一局游戏。
- 由服务端完整执行发牌、行动、计时、牌型比较和底池结算。
- 允许房主配置筹码、盲注、行动时间和筹码耗尽策略。
- 在每手牌之间提供明确的筹码请求、给予和准备阶段。
- 保存对局数据，支持非房主玩家掉线后恢复和重连。
- 提供筹码输赢排名及有趣、可解释的对局统计。

### 1.2 永久非目标

以下能力永远不在本项目范围内，不应出现在后续版本规划中：

- 公网大厅和公网匹配。
- 账号系统。
- 真实支付。
- 语音聊天。
- 跨设备房主迁移。
- 防恶意房主的分布式洗牌。
- 排位、商城和商业化系统。
- 复杂动画。

## 2. 角色与客户端

### 2.1 房主

- 房主必须使用 Windows 客户端创建房间。
- 房主必须入座并参与游戏，不提供“仅管理员”模式。
- 房主拥有房间设置、开始首局、暂停、继续、移除玩家和关闭房间等权限。
- 房主筹码耗尽后仍可管理房间和观战，但必须重新获得筹码后才能参赛。

### 2.2 普通玩家

- 普通玩家可以使用 Windows 客户端加入。
- 普通玩家也可以只使用手机或电脑浏览器参加完整游戏。
- 浏览器玩家通过房主提供的地址或二维码进入房间。
- 普通玩家不能修改房间规则或替代房主裁决游戏状态。

## 3. 联机与加入方式

### 3.1 Windows 客户端

Windows 客户端首页提供三个入口：

1. 创建房间。
2. 刷新局域网房间列表。
3. 手动输入房主 IP 或完整地址。

房间列表展示房间名称、房主、人数、当前状态、初始筹码、盲注、延迟和版本兼容状态。

### 3.2 浏览器

房主创建房间后展示连接地址和二维码，例如：

```text
http://10.126.126.1:32100
```

浏览器支持加入、准备、对局、筹码交换、统计查看和重连，但不支持创建房间或主动扫描局域网房间。

### 3.3 网络诊断

房主创建房间时应能看到：

- 当前选择的虚拟或实体网卡。
- 对外公布的 IPv4 地址。
- 游戏端口和发现端口。
- Windows 防火墙提示。
- 可复制的连接地址和二维码。

如果虚拟局域网不转发广播，玩家仍可通过手动输入房主 IP 加入。

## 4. 房间规则

### 4.1 人数与座位

- 最少 2 名玩家才能开始。
- 最多支持 10 名玩家。
- 不设置“默认几人桌”。牌桌布局和行动顺序根据实际参赛人数计算。
- 第一手开始后不接受新的参赛玩家，只允许已有玩家重连。新玩家加入中途观战不在当前范围内。

### 4.2 初始筹码

- 房主设置所有玩家的初始筹码。
- 初始筹码必须是正整数。
- 默认值为 2000。
- 第一手开始后不能修改初始筹码。

### 4.3 盲注

创建房间时提供以下小盲/大盲档位：

- 1 / 2
- 5 / 10
- 10 / 20
- 25 / 50
- 50 / 100
- 100 / 200
- 自定义

自定义模式只输入小盲，大盲始终由系统计算：

```text
大盲 = 小盲 × 2
```

小盲必须是正整数。系统不允许出现大盲不是小盲两倍的房间规则。

### 4.4 盲注增长

盲注按完成的手数增长，不按自然时间增长。

增长间隔提供：

- 不增长。
- 每 5 手。
- 每 10 手。
- 每 20 手。
- 自定义手数。

默认每 10 手增长一次，默认增长倍率为 2。增长倍率允许房主配置为大于 1 的数值。

增长时先计算新的小盲并向上取整为整数，再计算大盲：

```text
新小盲 = ceil(旧小盲 × 增长倍率)
新大盲 = 新小盲 × 2
```

盲注变化发生在上一手结算完成后、下一手准备阶段开始前，并向全体玩家显示提示。

### 4.5 计时

- 房主可配置单次行动时长。
- 默认单次行动时间为 30 秒。
- 超时且可以过牌时自动过牌，否则自动弃牌。
- 计时以服务端截止时间为准，客户端倒计时只负责展示。

### 4.6 筹码耗尽策略

房主可选择：

1. 请求其他玩家给予筹码。
2. 筹码耗尽后出局。

默认策略为“请求其他玩家给予筹码”。游戏只处理虚拟筹码转移，不处理真实付款。

## 5. 房间与牌局生命周期

```text
房间等待
  -> 全员准备
  -> 房主手动开始
  -> 第一手发牌与下注
  -> 摊牌或提前结束
  -> 结算与统计
  -> 手牌准备
  -> 后续手牌发牌与下注
  -> ...
  -> 房主关闭房间
```

### 5.1 第一手之前：房间等待

- 所有当前入座玩家必须主动点击“准备”。
- 第一手之前没有超时自动准备。
- 至少两人且全员准备后，房主的“开始游戏”按钮才可用。
- 第一手由房主手动开始，不自动开始。
- 任意玩家取消准备后，房主的开始按钮立即禁用。

### 5.2 每手之前：手牌准备

从第二手开始，每次结算后都进入独立的手牌准备阶段：

- 默认持续 30 秒，房主可在创建房间时调整。
- 该阶段用于请求、给予和确认筹码转移。
- 有筹码且可以参赛的玩家点击“已就绪”。
- 没有筹码的玩家必须完成筹码请求，或选择“本手暂不参与”。
- 存在待处理筹码请求时，不允许提前发牌。
- 所有玩家均进入“已就绪”或“本手暂不参与”的确定状态，且没有待处理请求时，立即发牌。
- 倒计时结束后，所有仍未确认的玩家自动暂离本手；只有主动确认“已就绪”的玩家才会参加下一手。

第一手前的“房间准备”和每手间的“手牌准备”必须在界面文案与状态模型中明确区分。

## 6. 德州扑克规则边界

本项目实现标准无限注德州扑克，使用一副不含大小王的 52 张牌。

### 6.1 支持的玩家状态

- 等待准备。
- 本手活跃。
- 已弃牌。
- 已全押。
- 本手暂离。
- 掉线并等待重连。
- 筹码耗尽并等待请求。
- 已出局。
- 已主动退出。

### 6.2 行动

- 弃牌。
- 过牌。
- 跟注。
- 下注。
- 加注。
- 全押。

服务端必须校验行动者、行动顺序、所需跟注额、最小下注、最小加注和全押后的再次加注资格。

### 6.3 庄家与盲注顺序

- 双人局中，庄家同时是小盲；翻牌前庄家先行动，翻牌后大盲先行动。
- 三人局中，庄家、小盲和大盲分别占据三个座位。
- 4 至 10 人局按标准顺时针顺序分配庄家、盲注和行动位置。
- 出局、主动退出和本手暂离玩家不参与角色分配。
- 掉线但仍保留座位的玩家正常获得位置，并在行动超时后自动过牌或弃牌。

### 6.4 结算

- 支持一名玩家未摊牌便赢得底池。
- 支持多名玩家摊牌比较。
- 进入摊牌时，服务端向所有当前玩家公开最后仍有资格竞争底池的玩家底牌；提前弃牌、未参与本手或未摊牌获胜的玩家底牌始终保持隐藏。
- 支持一个或多个边池。
- 支持平分底池。
- 无法均分的奇数筹码从庄家左侧开始，按仍有资格的玩家顺时针分配。

## 7. 筹码请求与给予

筹码只能在手牌准备阶段转移，已投入当前手牌底池的筹码永远不能转移。

### 7.1 主动给予

- 给予者选择接收玩家和筹码数量。
- 系统展示给予后的双方筹码余额。
- 给予者二次确认后立即完成转移。

### 7.2 请求筹码

- 请求者可以指定一名玩家，也可以向全桌发出请求。
- 请求包含期望数量和可选说明。
- 被请求玩家可以批准或拒绝。
- 全桌请求由第一名批准且余额足够的玩家完成，完成后自动关闭其他待处理入口。

### 7.3 一致性与记录

- 每次转移必须原子扣减给予者并增加接收者。
- 不允许给予超过当前可用筹码的数量。
- 允许给予者将可用筹码全部转出，但必须显著警告其将无法参加下一手。
- 所有成功、拒绝和撤销记录均进入公开的房间操作记录。
- 玩家筹码总量在转移前后保持不变。

## 8. 关闭、退出与重连

### 8.1 普通玩家主动关闭 Windows 客户端

显示“是否退出房间？”确认框：

- 默认操作为“退出房间”。
- 另一操作为“取消”。
- 确认退出后保留历史、统计和筹码记录，但座位不再参与后续手牌。

### 8.2 房主主动关闭 Windows 客户端

显示“是否关闭房间及当前对局？”确认框：

- 默认操作为“关闭房间”。
- 另一操作为“取消”。
- 确认后结束对局、保存最终结果并通知其他玩家。

### 8.3 意外掉线

- 网络中断、程序崩溃和网页标签关闭一律先视为意外掉线。
- 意外掉线不删除玩家、筹码、座位、手牌记录或统计数据。
- 服务端保留重连身份，玩家恢复连接后回到原座位。
- 掉线期间轮到该玩家行动时，按行动超时规则处理。
- 网页玩家必须使用游戏内“退出房间”按钮表达主动退出。

### 8.4 房主异常退出

- 房主进程异常退出时不把房间标记为正常关闭。
- 同一台房主电脑重新启动后，异常中断的对局保留为可恢复记录，不自动恢复最近一局。
- 不支持由其他设备接管房主。

### 8.5 对局记录与房主启动

- 每次创建房间均创建一条独立的对局记录；记录包含房间设置、房主、创建与最后活动时间、生命周期状态、最终统计及恢复所需快照和事件。
- 对局记录具有以下面向房主的状态：`进行中`、`异常中断可恢复`、`正常结束` 和 `已归档`。同一台房主电脑任一时刻最多运行一场对局。
- 房主 Windows 客户端启动后先显示对局记录管理页，而不是直接加载某个旧房间。房主可新建房间、恢复任一“异常中断可恢复”的对局，或查看与归档旧记录。
- 新建房间不会覆盖可恢复记录；房主可以稍后回到记录管理页恢复其中一场。创建、恢复和归档只能由本机房主操作，浏览器和其他 Windows 玩家不能访问这些操作。
- 正常关闭房间后保留最终统计并标记为“正常结束”；异常退出后保留最近一致快照和事件并标记为“异常中断可恢复”。归档仅从默认可恢复列表隐藏记录，不删除历史数据或统计。
- 房主可物理删除已归档记录。删除前必须展示受影响的对局名称和“删除后不可恢复”的提示，并要求房主二次确认；删除会一并移除该记录的事件、快照、玩家和统计数据。进行中、异常中断可恢复和正常结束记录不能直接删除。

## 9. 统计与局内称号

### 9.1 基础统计

- 当前筹码和筹码排名。
- 相对初始筹码的净输赢。
- 参与手数和赢得手数。
- 最大单手盈利。
- 最大赢得底池。
- 摊牌次数和摊牌胜率。
- 弃牌、过牌、跟注、加注和全押次数。

### 9.2 局内称号

- **All-in 之王**：全押次数最多。
- **倒霉蛋**：进入 1 对 1 摊牌后输掉次数最多。
- **底池收割机**：累计赢得底池筹码最多。
- **翻倍大师**：单手净盈利最高。
- **偷鸡王**：未进入摊牌便赢得底池次数最多。
- **河牌杀手**：河牌完成反超并获胜次数最多。
- **铁公鸡**：达到最低参与手数后，翻牌前弃牌比例最高。

并列时允许多人同时获得同一称号。所有统计均由服务端根据已确认的游戏事件计算。

## 10. 关键界面

### 10.1 联机大厅

- 创建房间。
- 刷新房间列表。
- IP 直连。
- 网络诊断。

### 10.2 房间等待页

- 座位、玩家和准备状态。
- 房间规则摘要。
- 玩家准备和取消准备。
- 房主开始、移除玩家和关闭房间。

### 10.3 牌桌页

- 公共牌、主池、边池和当前盲注。
- 各玩家座位、筹码、当前下注、状态和倒计时。
- 庄家、小盲、大盲标记，以及本轮和本手累计投入。
- 自己的底牌。
- 结算后的摊牌竞争者底牌。
- 弃牌、过牌、跟注、下注、加注和全押操作。
- 加注滑块及常用快捷值。
- 操作记录、统计入口和房主控制。
- 发牌、手牌准备、轮到自己或其他玩家、下注与弃牌等已确认状态变化提供简短音效；首次进入或重连时不补播历史音效。

### 10.4 手牌准备页或牌桌覆盖层

- 30 秒准备倒计时。
- 当前玩家就绪状态。
- 请求筹码、给予筹码和待审批请求。
- “已就绪”和“本手暂不参与”。

### 10.5 响应式要求

- 最低支持 360 CSS 像素宽度。
- 手机竖屏能够完成全部游戏操作，不要求切换横屏。
- 主要触控目标至少 44 × 44 CSS 像素。
- 手机端操作区固定在底部，不能被牌桌或系统安全区遮挡。
- 次要记录和统计在手机端使用抽屉或折叠面板。
- 任何关键状态不能只依赖鼠标悬停表达。

## 11. 产品验收原则

- 玩家不能通过客户端伪造筹码、牌面或行动结果。
- 浏览器和 Windows 客户端对同一房间呈现一致状态。
- 任何牌局状态都能解释当前行动者和合法行动集合。
- 除明确的筹码转移外，筹码不能凭空增加或消失。
- 非房主掉线不会导致玩家数据或对局数据被删除。
- 房主正常关闭和异常退出具有不同的持久化状态。
- 房间等待、手牌准备和实际对局是三个可区分的状态。

## 12. 后续详细实施方案约束

后续为 GPT-5.6 Luna 编写的实施方案必须同时以本文和 `docs/architecture.md` 为事实来源，并遵守：

- 按最小、可独立验证的逻辑模块拆分任务。
- 每次只实现一个模块，不把规则引擎、网络、持久化和 UI 混在同一步。
- 每个模块先声明输入、输出、不变量和依赖，再开始实现。
- 每个模块包含对应测试和明确的验证命令。
- 上一模块验收通过后才能进入依赖它的下一模块。
- 如实现发现本文存在歧义，应先修订文档并确认，不能在代码中静默假设。
