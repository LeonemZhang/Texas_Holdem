# Texas Hold'em 关键产品决策

> 状态：开发基线  
> 适用范围：`LeonemZhang/Texas_Holdem`  
> 本文描述产品目标、明确规则和关键交互。实现设计以 `docs/architecture.md` 为准。

## 1. 产品定位

本项目是一款供朋友之间通过实体局域网或虚拟局域网进行对战的无限注德州扑克游戏。

游戏不依赖公网服务。房主的 Windows 客户端同时运行房间服务器，其他玩家通过 Windows 客户端或浏览器连接房主。

### 1.1 核心目标

- 在虚拟局域网中稳定创建、发现和加入房间。
- 支持 Windows 桌面端和手机、电脑浏览器共同参与同一局游戏。
- 由服务端完整执行发牌、行动、计时、牌型比较和底池结算。
- 允许房主配置筹码、盲注、行动时间和筹码耗尽策略。
- 在每手牌之间提供明确的筹码请求、给予和准备阶段。
- 保存对局数据，支持非房主玩家掉线后恢复和重连。
- 提供筹码输赢排名及有趣、可解释的对局统计。

### 1.2 永久非目标

以下能力永远不在本项目范围内，不应出现在后续版本规划中：

- 公网大厅和公网匹配。
- 账号系统。
- 真实支付。
- 语音聊天。
- 跨设备房主迁移。
- 防恶意房主的分布式洗牌。
- 排位、商城和商业化系统。
- 复杂动画。

## 2. 角色与客户端

### 2.1 房主

- 房主必须使用 Windows 客户端创建房间。
- 房主必须入座并参与游戏，不提供“仅管理员”模式。
- 房主拥有房间设置、开始首局、暂停、继续、移除玩家和关闭房间等权限。
- 房主筹码耗尽后仍可管理房间和观战，但必须重新获得筹码后才能参赛。

### 2.2 普通玩家

- 普通玩家可以使用 Windows 客户端加入。
- 普通玩家也可以只使用手机或电脑浏览器参加完整游戏。
- 浏览器玩家通过房主提供的地址或二维码进入房间。
- 普通玩家不能修改房间规则或替代房主裁决游戏状态。

## 3. 联机与加入方式

### 3.1 Windows 客户端

Windows 客户端首页提供三个入口：

1. 创建房间。
2. 刷新局域网房间列表。
3. 手动输入房主 IP 或完整地址。

房间列表展示房间名称、房主、人数、当前状态、初始筹码、盲注、延迟和版本兼容状态。

Windows 客户端主窗口默认以当前显示器工作区内的普通最大化窗口启动，保留最小化、还原和关闭能力；还原窗口以 1920×1080 为目标并裁剪到启动显示器工作区内。桌面端最低支持环境为原生 1920×1080 显示器、Windows 100% 显示缩放和普通最大化窗口。更低分辨率、低高度还原窗口或更高显示缩放仅作尽力兼容，允许出现纵向滚动或紧凑布局，应用不阻止玩家进入房间、加入游戏，也不展示分辨率提示。应用不使用独占全屏、Kiosk、无边框窗口或固定分辨率。

Windows 客户端在可执行文件、原生窗口、任务栏、任务管理器进程组、桌面与开始菜单快捷方式、安装和卸载入口中统一显示产品名 `Texas Holdem` 及同一套德州扑克品牌图标，不得回退为 Electron 默认名称或图标。开发模式底层调试进程的文件名可以保留 `electron.exe`，但窗口标题和任务栏身份仍使用产品品牌。

Windows 客户端的 SQLite 对局记录、Electron 本地状态和缓存必须统一保存在 Windows 应用数据目录的 `Texas Holdem` 子目录中，不得在桌面创建或更新运行数据目录；外部启动参数也不得将应用运行数据重定向到桌面。

### 3.2 浏览器

房主创建房间后展示连接地址和二维码，例如：

```text
http://10.126.126.1:32100
```

浏览器支持加入、准备、对局、筹码交换、统计查看和重连，但不支持创建房间或主动扫描局域网房间。邀请链接和二维码携带房主地址，打开后自动预填；玩家必须先检测房间可连接，再输入昵称并确认加入。

进入牌局后，房主仍可在游戏中的房主管理面板复制当前房间邀请链接或二维码，方便玩家意外退出后重新进入。

浏览器标签页、收藏夹、添加到主屏幕、Web App manifest 和系统磁贴使用与 Windows 客户端一致的产品名、主题色和德州扑克品牌图标；通过房主 HTTP 服务访问和 Electron 本地加载时必须引用同一来源生成的资源。

### 3.3 网络诊断

房主创建房间时应能看到：

- 当前选择的虚拟或实体网卡。
- 对外公布的 IPv4 地址。
- 游戏端口和发现端口。
- Windows 防火墙提示。
- 可复制的连接地址和二维码图片。

如果虚拟局域网不转发广播，玩家仍可通过手动输入房主 IP 加入。

多网卡房主的发现响应以实际回复该 UDP 请求的源 IPv4 作为玩家连接目标；响应报文中其他接口的宣传地址不能覆盖这个可达地址。广播发现仍只是便利功能，手动 IP 直连继续作为独立兜底。

## 4. 房间规则

### 4.1 人数与座位

- 最少 2 名玩家才能开始。
- 最多支持 10 名玩家。
- 不设置“默认几人桌”。牌桌布局和行动顺序根据实际参赛人数计算。
- 房间等待页按当前房间人数上限显示对应数量的物理座位。桌面优先使用两列、按行填充的布局；例如 5 人房间显示为第一行 1/2、第二行 3/4、左下角 5。移动端只显示当前实际玩家卡片。
- 仅在第一手开始前，房主可以在连续座位中直接拖动大厅中的玩家卡片到另一名玩家卡片上，以原子交换两人的座位；空座位不可作为拖放目标。每次放下只提交一次权威换座命令，客户端等待房间快照后更新。若已有座位不连续，先通过“随机打乱”恢复紧凑排列后再允许拖动。大厅座位操作栏提供“修改房间配置”和“随机打乱”，随机结果由服务端生成并必须紧凑占据座位 1 至 N，且在至少两名玩家时产生不同于当前顺序的排列。
- 第一手开始后不接受新的参赛玩家，只允许已有玩家重连。新玩家加入中途观战不在当前范围内。

### 4.2 初始筹码

- 房主设置所有玩家的初始筹码。
- 初始筹码必须是正整数。
- 默认值为 100。
- 第一手开始后不能修改初始筹码。

### 4.3 盲注

创建房间时提供以下小盲/大盲档位：

- 1 / 2
- 5 / 10
- 10 / 20
- 25 / 50
- 50 / 100
- 100 / 200
- 自定义

自定义模式只输入小盲，大盲始终由系统计算：

```text
大盲 = 小盲 × 2
```

小盲必须是正整数。系统不允许出现大盲不是小盲两倍的房间规则。

### 4.4 盲注增长

盲注按完成的手数增长，不按自然时间增长。

增长间隔提供：

- 不增长。
- 每 5 手。
- 每 10 手。
- 每 20 手。
- 自定义手数。

盲注增长默认关闭。启用后默认每 10 手增长一次，默认增长倍率为 2。增长倍率允许房主配置为大于 1 的数值。

增长时先计算新的小盲并向上取整为整数，再计算大盲：

```text
新小盲 = ceil(旧小盲 × 增长倍率)
新大盲 = 新小盲 × 2
```

盲注变化发生在上一手结算完成后、下一手准备阶段开始前，并向全体玩家显示提示。

房间设置中的小盲/大盲是基准配置；牌桌状态行和玩家快照展示当前手或下一手实际生效的盲注级别。手牌准备的“可就绪”资格和下一手参赛校验也必须使用该当前大盲，不能继续使用增长前的配置值。

### 4.5 计时

- 房主可配置单次行动时长。
- 默认单次行动时间为 30 秒。
- 超时且可以过牌时自动过牌，否则自动弃牌。
- 计时以服务端截止时间为准，客户端倒计时只负责展示。

### 4.6 筹码耗尽策略

房主可选择：

1. 请求其他玩家给予筹码。
2. 筹码耗尽后出局。

默认策略为“请求其他玩家给予筹码”。游戏只处理虚拟筹码转移，不处理真实付款。

## 5. 房间与牌局生命周期

```text
房间等待
  -> 全员准备
  -> 房主手动开始
  -> 第一手发牌与下注
  -> 摊牌或提前结束
  -> 结算与统计
  -> 手牌准备
  -> 后续手牌发牌与下注
  -> ...
  -> 房主关闭房间
```

### 5.1 第一手之前：房间等待

- 房主创建房间后默认已准备；其余当前入座玩家必须主动点击“准备”。
- 第一手之前没有超时自动准备。
- 房主拖动或随机打乱座位不改变任何玩家的准备状态、筹码、身份或权限；首局庄位、盲注和行动顺序使用调整后的权威座次。
- 至少两人且所有非房主玩家准备后，房主的“开始游戏”按钮才可用。
- 第一手由房主手动开始，不自动开始。
- 任意非房主玩家取消准备后，房主的开始按钮立即禁用。
- 房主可以在首局开始前从大厅打开“修改房间配置”，修改房间名称、人数上限、初始筹码、盲注、计时、盲注增长和筹码耗尽策略；修改通过服务端命令生效并由最新房间快照同步给所有玩家。人数上限不得低于当前大厅玩家数；修改初始筹码时同步更新当前大厅玩家筹码，不改变准备状态。首局开始后不再允许修改房间配置。

### 5.2 每手之前：手牌准备

从第二手开始，每次结算后都进入独立的手牌准备阶段：

- 默认持续 30 秒，房主可在创建房间时调整。
- 该阶段用于请求、给予和确认筹码转移。
- 筹码不少于当前大盲注且可以参赛的玩家点击“已就绪”。
- 筹码低于当前大盲注的玩家必须完成筹码请求，或选择“本手暂不参与”。
- 存在待处理筹码请求时，不允许提前发牌。
- 所有玩家均进入“已就绪”或“本手暂不参与”的确定状态，且没有待处理请求时，立即发牌。
  - 倒计时结束后，所有仍未确认的玩家自动暂离本手；只有主动确认“已就绪”的玩家才会参加下一手。截止前已创建但未处理的请求保留：请求方本手暂离，其他已就绪玩家正常发牌，被请求方可在任意后续阶段处理该请求。
  - 若截止时不足两名玩家已就绪，准备阶段保持开放；筹码不少于当前大盲注的暂离玩家可点击“加入下一手”重新就绪。待处理请求仍阻止发牌；任意两名玩家重新就绪且请求处理完毕后立即发牌。

第一手前的“房间准备”和每手间的“手牌准备”必须在界面文案与状态模型中明确区分。

## 6. 德州扑克规则边界

本项目实现标准无限注德州扑克，使用一副不含大小王的 52 张牌。

### 6.1 支持的玩家状态

- 等待准备。
- 本手活跃。
- 已弃牌。
- 已全押。
- 本手暂离。
- 掉线并等待重连。
- 筹码耗尽并等待请求。
- 已出局。
- 已主动退出。
- 已被房主移出。

### 6.2 行动

- 弃牌。
- 过牌。
- 跟注。
- 下注。
- 加注。
- 全押。

服务端必须校验行动者、行动顺序、所需跟注额、最小下注、最小加注和全押后的再次加注资格。

### 6.3 庄家与盲注顺序

- 双人局中，庄家同时是小盲；翻牌前庄家先行动，翻牌后大盲先行动。
- 三人局中，庄家、小盲和大盲分别占据三个座位。
- 4 至 10 人局按标准顺时针顺序分配庄家、盲注和行动位置。
- 出局、主动退出、已被房主移出和本手暂离玩家不参与角色分配。
- 掉线但仍保留座位的玩家正常获得位置，并在行动超时后自动过牌或弃牌。
- 创建单手状态前按权威座位号稳定整理玩家；各街行动顺位只为当前仍可行动的玩家生成，牌桌展示从本人座位开始按顺时针排列。

### 6.4 结算

- 支持一名玩家未摊牌便赢得底池。
- 支持多名玩家摊牌比较。
- 进入摊牌时，服务端向所有当前玩家公开最后仍有资格竞争底池的玩家底牌；提前弃牌、未参与本手或未摊牌获胜的玩家底牌默认保持隐藏。
- 因弃牌提前结束时，不再补发公共牌；结算框只展示当时已经公开的公共牌。若仍有两名或以上未弃牌玩家且后续无人可行动（例如全押），服务端自动补齐至河牌后摊牌结算。
- 在本手结算完成至下一手开始前，已参与本手的玩家可主动选择“摊牌”公开自己的两张底牌；该操作仅能公开本人牌面、不可撤销，不改变赢家、底池或筹码。弃牌获胜时，只有赢家在此阶段主动摊牌并由服务端完成评估后，才将其牌型纳入牌型记录；所有玩家均可看到已公开的底牌。
- 支持一个或多个边池。
- 支持平分底池。
- 无法均分的奇数筹码从庄家左侧开始，按仍有资格的玩家顺时针分配。
- 某一贡献层只有一名玩家投入时，该层不构成可争夺底池，贡献额原样退回该玩家；多个主池/边池及奇数筹码处理后，所有派彩和退回额必须与底池总额相等。

## 7. 筹码请求与给予

筹码请求只能在手牌准备阶段创建；主动给予仍只能在手牌准备阶段发起。已创建请求可在任意阶段批准、拒绝或撤销。已投入当前手牌底池的筹码永远不能转移；对局中批准请求时，只在双方未投入的筹码间原子转移，并立即按服务端结果更新可用下注额。

### 7.1 主动给予

- 给予者选择接收玩家和筹码数量。
- 系统展示给予后的双方筹码余额。
- 给予者二次确认后立即完成转移。

### 7.2 请求筹码

- 请求者必须指定一名玩家，不提供面向全桌的请求。
- 请求包含期望数量和可选说明，且不得超过目标玩家当前可转出的筹码。
- 被请求玩家可以批准或拒绝。

### 7.3 一致性与记录

- 每次转移必须原子扣减给予者并增加接收者。
- 不允许给予超过当前可用筹码的数量。
- 允许给予者将可用筹码全部转出，但必须显著警告其将无法参加下一手。
- 待处理、成功、拒绝、撤销和主动给予全部进入按最近更新排序的公开房间操作记录；每条记录保存服务端权威的创建及最近更新时间，界面按本地时区显示最近更新时间的时、分、秒；记录跨手牌、重连和服务恢复保留。
- 玩家筹码总量在转移前后保持不变。

## 8. 关闭、退出与重连

### 8.1 普通玩家主动关闭 Windows 客户端

显示“是否退出房间？”确认框：

- 默认操作为“退出房间”。
- 另一操作为“取消”。
- 确认退出后统一记为 `left`，保留历史、统计、筹码、座位和原设备恢复身份；该座位不计入大厅人数、准备人数或后续手牌，且不清除原设备的恢复令牌。
- 同一设备再次进入该房间时，必须凭保存的恢复身份回到原玩家状态，不重新发放初始筹码；其他设备不能仅凭相同昵称恢复该身份。若退出发生在当前手，服务端沿用常规行动超时逻辑，能过牌就过牌，否则弃牌；恢复后该玩家本手暂不参与。
- 大厅阶段主动退出后，重新检测房间时显示原昵称作为初始值的可编辑恢复表单；确认恢复可修改昵称，但必须复用原令牌、`playerId` 和座位，不得创建第二个座位。昵称冲突时恢复失败并保留表单。
- 局内主动退出后的恢复不允许修改昵称，继续使用原昵称；普通刷新或意外掉线仍按原有自动恢复流程处理。
- 玩家可离开房间 A 后加入房间 B；两间房间的身份、筹码与统计彼此独立，A 的原设备恢复资格继续保留。

### 8.2 房主移出玩家

- 房主移出玩家统一记为 `removed`，被移出玩家保留座位、昵称、筹码、统计和历史；房间 roster、统计和历史可继续使用该记录，但牌桌视觉列表不显示任何 `removed` 玩家。
- 第一手开始后，房主只能在手牌结束后的准备阶段移出玩家。
- 对局中被移出玩家在该房间关闭前不得再提交任何命令或恢复身份；该限制不影响其加入其他房间。

### 8.3 房主主动关闭 Windows 客户端

显示“是否关闭房间及当前对局？”确认框：

- 默认操作为“关闭房间”。
- 另一操作为“取消”。
- 确认后结束对局、保存最终结果并通知其他玩家。最终快照送达房主客户端后，桌面端停止宿主服务并释放游戏端口；房主新建下一间房间时可重新选择网卡。

### 8.4 意外掉线

- 网络中断、程序崩溃和网页标签关闭一律先视为意外掉线。
- 意外掉线不删除玩家、筹码、座位、手牌记录或统计数据。
- 服务端保留重连身份，玩家恢复连接后回到原座位。
- 掉线期间轮到该玩家行动时，按行动超时规则处理。
- 网页玩家必须使用游戏内“退出房间”按钮表达主动退出。

### 8.5 房主异常退出

- 房主进程异常退出时不把房间标记为正常关闭。
- 同一台房主电脑重新启动后，异常中断的对局保留为可恢复记录，不自动恢复最近一局。
- 不支持由其他设备接管房主。

### 8.6 对局记录与房主启动

- 每次创建房间均创建一条独立的对局记录；记录包含房间设置、房主、创建与最后活动时间、生命周期状态、最终统计及恢复所需快照和事件。
- 对局记录具有以下面向房主的状态：`进行中`、`异常中断可恢复`、`正常结束` 和 `已归档`。同一台房主电脑任一时刻最多运行一场对局。
- 房主 Windows 客户端启动后显示牌桌大厅，而不是自动加载旧房间。若桌面端检测到仍在本机运行的房主服务及其“进行中”记录，必须在“IP 直连到房主牌桌”上方显示对局摘要和“恢复对局”按钮；恢复后回到该运行房间。对局记录管理页显示每条记录最近一次联机所用的网卡名称和 IPv4；旧记录明确标记为未保存网卡，房主可在其中新建房间、恢复任一“异常中断可恢复”的对局，或查看与归档旧记录。
- 恢复对局时优先自动复用该记录保存且仍存在于本机的 IPv4；旧记录或原网卡不可用时才要求房主选择网卡，成功恢复后更新该记录的网卡。记录管理本身不对局域网开放服务。
- 网卡选择是创建或恢复当前对局的一次性表单状态，不是应用级设置，也不影响扫描、直连、诊断或其他对局。只有成功创建或恢复后才将该次实际联机网卡写入对应记录；退出、关闭或未创建房间时必须丢弃选择，下次进入重新选择。
- 若本地已有进行中对局而房主选择创建新房间，必须先明确选择“恢复上次对局”或“关闭上次对局并创建新房间”。后者按正常关闭流程保存旧局最终状态、通知玩家、停止宿主服务并释放端口；表单保留原设置，房主在创建新局时选择网卡。创建、恢复和归档只能由本机房主操作，浏览器和其他 Windows 玩家不能访问这些操作。
- 正常关闭房间后保留最终统计并标记为“正常结束”；异常退出后保留最近一致快照和事件并标记为“异常中断可恢复”。归档仅从默认可恢复列表隐藏记录，不删除历史数据或统计。
- 房主可物理删除已归档记录。删除前必须展示受影响的对局名称和“删除后不可恢复”的提示，并要求房主二次确认；删除会一并移除该记录的事件、快照、玩家和统计数据。进行中、异常中断可恢复和正常结束记录不能直接删除。
- 记录管理的每条记录均可打开“查看统计”弹窗；弹窗复用局内统计的内容与标签页，不向 LAN 或浏览器暴露。历史战报包含已评估牌型的实际五张牌面；提前获胜仅在当时已有至少五张可评估牌时记录赢家牌面，翻牌前不补发公共牌或伪造牌型。

## 9. 统计与局内称号

### 9.1 基础统计

- 当前筹码和筹码排名。
- 筹码排名仍按当前筹码从高到低排列，但状态为 `removed` 的玩家始终排在所有未被踢出玩家之后；同类玩家之间继续按当前筹码排序。
- 净输赢仅累计每手结算的筹码净变化；筹码请求、批准和主动给予等交换不计入该值。
- 参与手数和赢得手数。
- 最大单局盈利。
- 最大单局输掉（单手结算净亏损的最大绝对值，不含筹码交换）。
- 摊牌次数和摊牌胜率。
- 弃牌、过牌、跟注、加注和全押次数。

### 9.2 局内称号

- **All-in 之王**：全押次数最多。
- **倒霉蛋**：进入 1 对 1 摊牌后输掉次数最多。
- **底池收割机**：累计赢得底池筹码最多。
- **翻倍大师**：单手净盈利最高。
- **偷鸡王**：未进入摊牌便赢得底池次数最多。
- **河牌杀手**：河牌完成反超并获胜次数最多。
- **铁公鸡**：达到最低参与手数后，翻牌前弃牌比例最高。

并列时允许多人同时获得同一称号。所有统计均由服务端根据已确认的游戏事件计算。

“全押”只统计服务端接受的全押行动；“河牌杀手”只在完整五张公共牌的摊牌中，根据服务端比较河牌前后的最佳牌型确认反超。铁公鸡的比例在界面按百分比保留两位小数。

### 9.3 牌型记录与称号说明

- 统计提供“牌型记录”页：展示本局最高的完整五张牌型、全部并列归属玩家，以及每位玩家的最高牌型和五张牌面。
- 牌型记录统计摊牌结算中服务端评估的牌型；提前弃牌获胜时，仅统计结算阶段主动摊牌并完成服务端评估的赢家牌型，未主动摊牌的赢家不计入全局最高牌型和个人最高牌型。
- 同一牌型类别按完整踢脚牌比较；客户端不参与比较、归属或牌面推导。
- 每个称号提供可访问的“？”说明，准确说明其服务端计算口径；“倒霉蛋”为进入 1 对 1 摊牌后落败次数最多。
- 旧记录缺少牌型摘要时必须提示历史覆盖不足，不得虚构牌型或牌面。

## 10. 关键界面

### 10.1 联机大厅

- 创建房间。
- 刷新房间列表。
- IP 直连。
- 扫描牌桌和网络诊断分别进入独立页面，并可返回大厅。

### 10.2 房间等待页

- 桌面端使用固定两列五行座位表：左列座位 1–5、右列座位 6–10，空位仍展示；手机端仅以单列展示实际玩家。座位卡使用固定行高，列表占据剩余空间并独立滚动。
- 座位、玩家和准备状态；房主只能将玩家卡片拖到另一名玩家卡片上以交换顺位，空座位仅展示且不可投放；不设置“调整座位”按钮及弹窗；桌面端“随机打乱”作为唯一独立座位按钮，置于座位表左列下方，由服务端生成紧凑排列；房主“开始游戏”与普通玩家“准备”入口一样靠左放置。
- 房间规则摘要。
- 玩家准备和取消准备。
- 房主开始、移除玩家和关闭房间。

### 10.3 牌桌页

- 公共牌、总池、按翻牌前/翻牌/转牌/河牌纵向排列的本手下注历史和当前盲注；总池始终显示，当前街实时更新，已结束街固定显示最终金额。正常对局时牌局进度、倒计时、公共牌、底池纵列和本人底牌按独立流式行排列，后三者相对牌桌水平居中且不得互相遮挡；过长牌局进度使用单行省略号，完整内容仍可由桌面端悬停标题读取。
- 当本人拥有至少五张可用牌时，底牌旁显示服务端计算的当前最佳牌型；少于五张时不虚构牌型。结算时展示服务端已授权的牌型和最佳五张牌。
- 各玩家座位、筹码、当前下注、状态和倒计时；结算时展示本手净变化和已授权的牌型。
- 庄家、小盲、大盲标记，以及本轮和本手累计投入。
  - 座位卡不展示底牌；正常对局时牌桌中央展示本人的底牌。进入结算后，牌桌中央不展示公共牌、底池或任何玩家底牌；结算框顶部展示本手已公开的公共牌、总池和已发生街道的底池记录。
  - 结算框展示每位玩家的结算结果：玩家名称后展示服务端当前权威筹码，再展示本手净变化；先展示已授权的两张底牌，再展示按牌型排序的最佳五张牌，未摊牌玩家展示两张背牌。公共牌、玩家底牌和最佳五张牌使用相同标签列，使实际卡牌左边界一致。结算通过卡片内部“本手结算 + 收起”标题行折叠，收起按钮使用独立的青绿色描边胶囊样式，不复用工具抽屉头部；收起入口在桌面和手机端均置于牌桌中央进度文字正下方；新一手自动展开。主动“摊牌”入口位于结算准备框顶部操作区的“就绪”之后，使用紧凑蓝底样式并保留至少 44px 点击区域。服务端确认主动摊牌后，结算框展示其公开的两张底牌。
- 弃牌、过牌、跟注、下注、加注和全押操作；桌面跟注按钮中的金额以同一行内的紧凑徽标展示，不得因金额位数换行。
- 加注滑块及常用快捷值；快捷筹码以当前“加注至”金额为基准递进，并始终受服务端下发的最小、最大加注额约束。桌面加注滑块与本轮已投、本手累计和本轮最高三项统计使用相同的紧凑宽度并在筹码区左侧靠右排列，手机加注弹层仍使用可用全宽。
- 手机端将加注拆成“调整加注”和“确认加注”两个持续可达的动作：调整只修改并保留草稿金额，确认才提交服务端命令；未调整时确认最小合法加注。加注弹层不得遮住确认入口，紧凑筹码的可视圆盘可以缩小，但触控区仍不得小于 44 × 44 CSS 像素。
- 操作记录、统计入口和房主控制。
- 已确认的同手筹码投入以从座位飞向总池的短暂动画反馈，不自行推导或改写服务端金额。
- 发牌、手牌准备、轮到自己或其他玩家、下注、弃牌以及结算输赢/持平等已确认状态变化提供简短音效；首次进入或重连时不补播历史音效。只有轮到本人且服务端提供有效行动截止时间时播放“滴→答”行动提示，下一次“滴”按上一次“滴”的起始时刻固定间隔 2 秒；换人、行动完成、截止或离开牌局后立即停止。

### 10.4 手牌准备页或牌桌覆盖层

- 30 秒准备倒计时；超时且不足两人时显示“等待就绪”状态。
- 当前玩家就绪状态。
- 请求筹码、给予筹码和待审批请求。
- “已就绪”、满足资格时的“摊牌”和“本手暂不参与”；摊牌入口按此顺序紧随就绪操作。

### 10.5 响应式要求

- 最低支持 360 CSS 像素宽度。
- 手机竖屏能够完成全部游戏操作，不要求切换横屏。
- 主要触控目标至少 44 × 44 CSS 像素。
- 手机端操作区固定在底部，不能被牌桌或系统安全区遮挡；打开统计、筹码交换或房主管理时隐藏下注区和加注弹层，工具内容必须能够滚动至底部，关闭后恢复此前加注草稿。
- 手机顶部座位使用可横向滚动和吸附的行动队列，始终包含房间权威快照中的全部玩家。每手及每条街开始时按服务端行动顺位重排，同一轮内保持顺序不变；当前行动者变化时仅调整滚动位置，使已行动玩家保留在左侧、待行动玩家位于右侧。右侧剩余玩家超出视口时当前行动者尽量左对齐，剩余玩家已能完整显示时不得通过队尾空白强制贴左。本人在队列中始终使用不可交互的摘要卡，摘要卡与其他玩家座位卡展示相同的顺位、位置标记、行动、筹码、状态、结算和本轮下注信息；真实本人座位仍固定在牌桌下沿。
- 筹码交换、统计和房主管理共用统一工具抽屉头部及单一“收起”按钮；桌面使用右侧抽屉，手机使用全屏面板，同一时刻只显示一个工具面板。筹码交换以“筹码交换/公开记录”切换，统计以“牌局统计/局内称号”切换，房主管理不增加标签页。
- 桌面和手机端的普通玩家退出房间入口均位于牌桌顶部工具栏最右侧，与筹码交换、房主管理和查看统计同层；工具按钮组可横向滚动，退出入口不可收缩或被结算层覆盖。默认显示至少 44 × 44 CSS 像素的“×”，首次点击在原位置展开“退出房间”，第二次点击才显示确认；点击外部、按 Escape 或取消确认后恢复为“×”。
- 任何关键状态不能只依赖鼠标悬停表达。
- 响应式判断以浏览器或 Electron 的实际可用视口为准；手机端必须适应地址栏、底部工具栏和安全区变化，桌面端不得假定固定任务栏高度。
- 桌面牌桌使用顶部状态、中间牌桌和底部操作三个稳定区域；手机端允许复用业务组件并采用独立的紧凑组合，不能把桌面覆盖层直接等比压缩到窄屏。
- 正常对局中的公共牌、底池纵列和本人底牌相对牌桌水平居中；结算详情中的公共牌、玩家底牌和最佳五张牌保持实际卡牌左边界一致。桌面默认使用约 16:9、最大 80rem 的宽桌布，十人局采用专属紧凑座位环带；本人座位和底牌不得互相遮挡。低高度还原窗口保留纵向滚动作为尽力兼容，但不属于桌面支持基准。
- 桌面布局以原生 1920×1080 显示器、Windows 100% 显示缩放和普通最大化窗口作为最低支持环境；低于该条件仍可运行，但不保证无需滚动或保持完整桌面布局。

## 11. 产品验收原则

- 玩家不能通过客户端伪造筹码、牌面或行动结果。
- 浏览器和 Windows 客户端对同一房间呈现一致状态。
- 任何牌局状态都能解释当前行动者和合法行动集合。
- 除明确的筹码转移外，筹码不能凭空增加或消失。
- 非房主掉线不会导致玩家数据或对局数据被删除。
- 房主正常关闭和异常退出具有不同的持久化状态。
- 房间等待、手牌准备和实际对局是三个可区分的状态。

## 12. 后续详细实施方案约束

后续为 GPT-5.6 Luna 编写的实施方案必须同时以本文和 `docs/architecture.md` 为事实来源，并遵守：

- 按最小、可独立验证的逻辑模块拆分任务。
- 每次只实现一个模块，不把规则引擎、网络、持久化和 UI 混在同一步。
- 每个模块先声明输入、输出、不变量和依赖，再开始实现。
- 每个模块包含对应测试和明确的验证命令。
- 上一模块验收通过后才能进入依赖它的下一模块。
- 如实现发现本文存在歧义，应先修订文档并确认，不能在代码中静默假设。
