# GPT-5.6 Luna 增量小模块开发计划

> 目标模型：GPT-5.6 Luna  
> 默认推理强度：Medium  
> 复杂规则任务：High  
> 执行单位：一次调用只执行一个任务 ID  
> 前置条件：`docs/plans/terra-foundation-plan.md` 已完成且全套质量门禁通过

## 1. 计划目的

本计划把已评审的产品和架构基线拆成可以由 Luna 逐个完成、逐个测试、逐个验收的小模块。

本计划不是待办事项大纲。每个任务 ID 都是独立执行边界，不能把同一阶段的多行任务合并为一次“大功能实现”。

## 2. 必读事实来源

每次执行任意 Luna 任务前必须阅读：

1. 根 `AGENTS.md`。
2. `docs/product-spec.md`。
3. `docs/architecture.md`。
4. 本文的执行契约、当前任务行和直接依赖任务行。
5. 当前任务涉及的现有源码与测试。

产品规则以 `product-spec.md` 为准，技术边界以 `architecture.md` 为准。本文只决定实现顺序和任务边界。

## 3. Luna 单任务执行契约

### 3.1 开始前

- 确认 Terra 基础框架质量命令全部成功。
- 检查 Git 状态，列出已有改动并保留无关改动。
- 确认当前任务的所有依赖 ID 已在代码中完成，而不是仅在文档中勾选。
- 只打开当前任务、直接依赖模块和必要测试构造器。
- 不重新选择架构、依赖管理器或应用边界。

### 3.2 修改范围

- 一次只执行一个任务 ID。
- 只修改任务指定的主要目录，以及为导出、测试或文档索引所必需的最小关联文件。
- 不顺手实现下一任务。
- 不引入当前任务不需要的新运行时依赖。
- 不把业务逻辑放入 React、Socket.IO handler、Fastify route 或 Electron IPC。
- 不通过 `any`、跳过测试、关闭 lint 或弱化 schema 绕过问题。

### 3.3 每个任务必须交付

- 一个明确、窄化的公共行为。
- 对应单元测试或薄集成测试。
- 对新增公共接口的导出。
- 对关键不变量和错误分支的测试。
- 当前 workspace 的测试、类型检查和根 lint 结果。
- 实际改动与计划偏差说明。

### 3.4 任务完成定义

任务只有在以下条件全部满足时才算完成：

- 当前任务的完成条件全部满足。
- 当前模块测试成功。
- 根 `pnpm typecheck` 和 `pnpm lint` 成功。
- 没有破坏已完成任务的测试。
- 没有新增无关功能或未解释的 TODO。
- Git diff 只包含当前任务必要改动。

### 3.5 建议推理强度

| 任务类型                             | 推理强度      |
| ------------------------------------ | ------------- |
| schema、适配器、简单 UI 展示         | Low 或 Medium |
| 普通纯函数、服务薄集成、持久化仓储   | Medium        |
| 牌型、下注、边池、状态机、恢复一致性 | High          |

提高推理强度不能扩大任务范围。

## 19. 全局阶段门禁

阶段必须按以下顺序推进：

```text
Terra 基础框架
-> A 牌与牌型
-> B 座位
-> C 下注
-> D 底池
-> E 牌局状态机
-> F 房间领域
-> G 统计
-> H 协议
-> I 房主内存服务
-> J SQLite
-> K 局域网
-> L 共用客户端
-> M Electron
-> N 端到端验收
```

规则：

- 当前阶段门禁未通过，不进入下一阶段。
- 同一阶段内仍按依赖列执行，不能无视任务依赖并行修改共享文件。
- 发现前置模块缺陷时，先创建针对该前置任务的修复任务，不在当前任务中扩大范围。
- 产品决策变化必须先修改并重新评审产品/架构文档，然后更新本计划受影响任务。

## 20. 每阶段通用验证

每个任务至少运行：

```text
pnpm --dir <当前 workspace 路径> test
pnpm --dir <当前 workspace 路径> typecheck
pnpm lint
pnpm typecheck
```

每个阶段结束额外运行：

```text
pnpm format:check
pnpm test
pnpm build
```

涉及浏览器或 Electron 的阶段再运行：

```text
pnpm test:e2e
```

如果 Terra 最终生成的 workspace 脚本名称略有不同，应先通过 `AGENTS.md` 统一为稳定根命令；Luna 不应在每个任务中重新发明验证命令。

## 21. 计划完成定义

只有以下条件全部满足，整个 Luna 增量计划才完成：

- 所有任务 ID 均按单任务边界实现并验证。
- 产品文档中的核心目标全部存在端到端验收。
- 永久非目标没有进入源码、依赖或隐藏开关。
- 牌型、下注、边池和状态机具有确定性及独立测试。
- 服务端是唯一权威状态来源。
- 房主桌面端与手机/电脑浏览器能共同完成对局。
- 第一手必须全员准备后由房主手动开始。
- 后续每手具有 30 秒筹码交换与就绪阶段。
- 盲注包含 1/2 档、大盲始终两倍、按手数增长。
- 非房主掉线数据保留，房主正常和异常关闭语义不同。
- 统计和局内称号能由持久化事件重建。
- Windows 构建产物通过最小联机 smoke check。

## 22. 模型使用依据

Codex 官方模型说明将 Luna 定位为适合目标明确、可重复和高吞吐的聚焦任务。本文因此为每次执行提供单一任务 ID、固定事实来源、显式依赖、目录范围、完成条件和验证命令；需要复杂扑克规则判断的任务仍使用 Luna High，但不把多个模块合并。
