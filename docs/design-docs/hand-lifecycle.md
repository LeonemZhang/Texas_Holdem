# 牌局生命周期设计

本文负责把 `poker-domain` 原语编排成整手牌和连续牌局状态流转，不重新定义牌型、下注或派彩算法。

## 状态顺序

```text
LOBBY
-> PRE_HAND_READY
-> PREFLOP
-> FLOP
-> TURN
-> RIVER
-> SHOWDOWN
-> SETTLEMENT
-> PRE_HAND_READY
```

实现还需要表达 `PAUSED` 和 `CLOSED` 两类房间级状态。`LOBBY` 中房主默认已准备；所有非房主玩家准备后只启用房主开始命令，不自动转换到 `PRE_HAND_READY` 或 `PREFLOP`。首局由房主开始命令直接创建牌局；后续牌局必须先经过 `PRE_HAND_READY`。

服务端保存状态版本和准备/行动的绝对截止时间，客户端只展示。准备截止时服务端将未确认玩家投影为本局 `sitting-out`，但不销毁仍处于准备阶段的上下文或待处理筹码请求；不足两名就绪时不创建新局。后续沿用“设置准备选择”命令接受筹码不少于当前有效大盲的玩家重新就绪，待处理请求继续阻止创建下一局。

## 单手编排

1. 根据权威连续座位整理本局玩家、轮转庄家并注入盲注。
2. 发两张底牌，创建翻牌前下注轮。
3. 当前下注轮关闭后发翻牌三张，重置街道投入但保留累计投入。
4. 依次关闭翻牌、转牌和河牌下注轮，分别发一张转牌和河牌。
5. 若只剩一名未弃牌玩家，提前结束且不补发无关公共牌；若多人仍有资格，进入摊牌。
6. 若下注轮关闭、至少两名玩家仍具备竞争资格且无人可以继续行动，建立自动 Runout 计时链；每次只调用核心层单街推进，从当前街道等待 `2s` 后公开下一街道，依次公开翻牌、转牌和河牌。
7. 生成稳定单局摘要、公开范围、净变化和结算事件，保存后进入下一局准备。

自动 Runout 的每次街道推进都递增房间 `stateVersion` 和事件 `sequence`，先持久化当前权威状态，再向每名玩家发布过滤后的专属快照。河牌公开后不立即结算，另等待 `1s` 才进入摊牌；普通下注轮推进、河牌正常结束和弃牌提前结束不进入这条延迟链。

任何阶段推进都必须由服务端根据领域结果决定，客户端不能以本地按钮、倒计时或玩家数量推断并推进阶段。Runout 与底池构造、未匹配贡献退回和派彩保持独立。

## 连续牌局

只有成功结算后才增加完成局数并轮转庄家。盲注增长在结算完成、下一局准备开始前生效，并向所有玩家提示。下一局有效大盲决定准备资格和参赛者；不能使用增长前的基准值判断可就绪玩家。

当前局号由 Host 快照投影根据 `completedHands` 和当前牌局是否已结算确定：未结算牌局为 `completedHands + 1`，已结算牌局为 `completedHands`。因此结算和 `PRE_HAND_READY` 窗口保持刚结束的局号，只有下一局创建后才显示下一局号；`room.completedHands` 的递增时机和完成局数语义不变。

首局前的房间准备和局间牌局准备使用不同状态和不同文案；后者允许筹码请求/给予、明确就绪或暂不参与，并遵守待处理请求阻塞规则。

## 暂停、关闭与恢复

暂停只冻结允许的服务端调度，不把客户端倒计时当作恢复依据；暂停、关闭和销毁都必须清理自动 Runout 计时器。恢复时从已持久化的当前街道和房间状态重建单一计时器，继续剩余街道，不重放已公开街道、不跳过街道、不并行启动计时器。正常关闭必须先完成最终结果持久化并发布关闭事件；异常退出不能伪造正常关闭，恢复逻辑由 `persistence-and-recovery.md` 负责。
