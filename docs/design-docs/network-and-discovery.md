# 网络与发现设计

网络模块位于 `packages/lan-discovery`、`apps/host/src/discovery` 和桌面网络适配器，负责发现、地址解析和健康检查，不承担房间领域规则。

## 端口

- HTTP 与 Socket.IO：`32100/TCP`。
- 房间发现：`32101/UDP`。
- 端口允许在后续配置中覆盖，但发现报文必须携带实际端口。

## 发现流程

1. Windows 适配器枚举实体和虚拟 IPv4 网卡及可用广播地址。
2. 用户点击刷新后，扫描器向候选广播地址发送带协议版本和请求 ID 的发现请求。
3. 房主服务单播响应房间摘要、协议版本和连接地址。
4. 扫描器以 UDP 响应的实际源 IPv4 覆盖不匹配的宣传地址，确保多网卡房主返回可达 TCP 目标。
5. 客户端按 `roomId` 去重，按最后响应时间移除过期结果，并使用 TCP 健康检查验证房间确实可连接。

广播响应只是便利功能。手动输入裸 IP 自动补默认端口，完整 URL 可解析；发现失败不能阻止 IP 直连。扫描结果交给共用客户端完成加入交互：桌面端点击可加入房间后直接打开昵称弹窗，确认昵称后再解析当前房间并提交加入。大厅阶段存在待恢复身份时预填原昵称，确认可修改昵称并复用原令牌、`playerId` 和座位；进行中的房间恢复继续使用原昵称。

## 多网卡与诊断

房主创建房间时向客户端提供实际选择的网卡、公布 IPv4、游戏端口、发现端口、防火墙提示、可复制地址和二维码。发现响应中其他接口的宣传地址不能覆盖实际回复源地址。网卡选择只属于当前创建/恢复操作，成功后写入对应记录，不作为全局设置，也不影响扫描、直连、诊断或其他房间。

## 资源边界

发现器和响应器必须可关闭，不能持有未释放 UDP 资源；Socket/HTTP 健康检查也必须在服务关闭时释放。网络消息是不可信输入，先经过协议 schema 校验。`lan-discovery` 可以依赖协议类型和 Node 网络适配器，但不依赖 Electron；Electron 只负责枚举网卡和调用可关闭的适配器。
