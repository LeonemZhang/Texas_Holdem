# 持久化与恢复设计

持久化层是房主本机的适配器，不改变房间领域和 `poker-core` 的规则。运行中的房间以内存中的权威状态为准，SQLite 负责事件、快照和房主记录管理；项目不依赖云数据库或公网同步。

## 数据模型

每次创建房间建立一条独立记录，至少包含：

- `rooms`：房间设置、房主、创建时间、最后活动时间和生命周期状态。
- `players`：身份、座位、筹码、状态和恢复元数据。
- `events`：接受命令产生的顺序事件。
- `snapshots`：关键状态转换和每局结算后的恢复快照。
- `hand_summaries`：已完成牌局、公开牌面、结算和统计输入。
- `chip_transfers`：请求、给予、批准、拒绝、撤销和服务端时间戳。
- `statistics`：可从事件和牌局摘要重建的缓存，不是唯一事实来源。

## 写入规则

接受命令后，内存领域先完成变更；事件或筹码转移与必要快照在同一事务中持久化，事务成功后才向客户端确认。关键状态转换、每局结算和正常关闭必须保存快照。事件顺序和 `stateVersion` 用于重连补发和快照回退。

除初始化外，房间筹码总量保持不变；净输赢只归约已确认牌局结算的 `netChanges`，不读取 `chip_transfers` 或房间当前筹码，以隔离筹码交换对统计的影响。牌型比较和牌面评估只在 `poker-core`/host 完成，renderer 只渲染已投影的类别、归属和牌面。

## 生命周期与恢复

- 正常关闭写入最终状态和 `CLOSED` 事件，并保留最终统计。
- 房主进程异常退出不伪造正常关闭，记录标记为 `INTERRUPTED`，保留最近一致快照和事件。
- 房主启动后默认进入大厅，不自动载入旧房间。检测到本机仍运行的房主服务及其 `RUNNING` 记录时，才显示恢复入口；异常中断记录必须由房主明确选择恢复。
- 同一宿主服务一次只能载入一条运行记录。若已有进行中记录而房主创建新房间，桌面端必须先恢复旧局，或按正常关闭流程保存旧局、通知玩家、停止服务并等待端口释放后创建。
- 记录管理只能通过本机受限 IPC 访问，不监听 LAN HTTP、Socket.IO 或 UDP；浏览器和普通玩家不能恢复、归档或删除记录。
- 归档是可逆的目录状态变化，不删除事件、快照、玩家、牌型或统计。只有已归档记录能经对局名称展示和二次确认物理删除，并通过外键级联移除其关联数据。

恢复时优先复用记录保存且仍属于本机的 IPv4；旧记录或原网卡不可用时才要求房主选择网卡，成功恢复后保存新的实际网卡。网卡选择属于一次创建/恢复表单状态，退出、关闭或未成功创建时丢弃，不保存为全局宿主配置。

## 迁移与历史覆盖

持久化迁移必须保留旧记录向后兼容边界。缺少关键字段或旧记录没有牌型摘要时明确提示历史覆盖不足，不虚构牌型、牌面、网卡或结算结果。记录管理中的统计弹窗复用局内统计标签页，但不向 LAN 或浏览器暴露房主历史管理。

## 时间与随机数

服务端使用单调时间计算行动和准备阶段截止时间，对外事件携带绝对截止时间；核心逻辑使用注入的虚拟时钟。生产洗牌使用系统密码学安全随机源，测试使用可注入确定性随机源；领域包不能直接读取系统时间或全局随机函数。
